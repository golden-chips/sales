## 1. تقرير نظام المناديب والتوزيع

### 1.1 الحجم والمعمارية

| الجزء | التقنية | الحجم الفعلي |
|---|---|---|
| الخادم | Firebase Cloud Functions v2 (Node 22, JavaScript) | 25,456 سطرًا؛ `functions/index.js` وحده **10,905 أسطر**؛ **163** دالة مُصدَّرة |
| لوحة الإدارة | React 18 + Vite + TypeScript (PWA) | 55,585 سطرًا؛ 56 صفحة؛ 73 مكوّنًا |
| تطبيق المندوب | Expo / React Native + نسخة Web | 31,953 سطرًا؛ 32 شاشة |
| قاعدة البيانات | Cloud Firestore (NoSQL) | 78 قاعدة `match` في `firestore.rules`؛ نموذج بيانات موثّق في `DATA_MODEL.md` |
| تكاملات | Meta WhatsApp Cloud API، PDF عبر Chromium، Anthropic (محلل أداء + مساعد)، خرائط Google/Leaflet | — |

**المعمارية:** نظام Serverless أحادي المستأجر (شركة واحدة)، المنطق الحرج في Cloud Functions (triggers + callable)، والواجهات تقرأ Firestore مباشرة مع قواعد أمان.

### 1.2 الوظائف الموجودة (موثّقة من الكود)

- **المناديب والسيارات:** إنشاء مندوب بـ PIN مشفّر bcrypt عبر دالة (`createRep`, `setRepPin`)، ربط سيارة، تبديل السيارة، صيانة دورية بالكيلومتر، انتهاء الرخصة/الفحص/التأمين، تصاريح القيادة.
- **الورديات (Shifts) واليوم:** بدء/إنهاء وردية، تقرير نهاية اليوم كـ PDF وواتساب (`onShiftEnded`, `generateShiftReportPdf`)، مراجعة واعتماد يوم العمل (`reviewShift`).
- **الفوترة الميدانية:** فاتورة بخصم لكل صنف، نقدي/حوالة/آجل، سقف ائتمان، **ترقيم تسلسلي آمن أوفلاين** (`reserveNumberBlock` — حجز كتل أرقام)، توقيع استلام (POD)، PDF رسمي بالتفقيط العربي و QR.
- **التحصيل والديون:** دفعات على الآجل (`onPaymentCreated`)، أعمار الديون، تذكيرات واتساب، كشف حساب PDF، دفعات مقدمة، حوالات بانتظار التأكيد مع إيصال وقراءة إيصال بالذكاء الاصطناعي.
- **المرتجعات:** تخفيض قيمة الفاتورة وعكس العمولة (المرتجع لا يعود للمخزون — يُعتبر تالفًا).
- **مخزون السيارة:** تحميل صباحي عبر طلب يعتمده المسؤول، تسوية آخر اليوم (محمّل − مباع = راجع متوقع) مع تنبيه الفروقات، نقل مخزون بين السيارات.
- **المخزن الرئيسي** (`warehouse.js`): رصيد لكل صنف + سجل حركات + محجوز للطلبات + حد طلب.
- **التصنيع المبسّط** (`manufacturing.js`, 1,659 سطرًا): مواد خام، خلطات (recipes)، عجن وتعبئة، توريد وصرف، جهات (المعمل/موزعون)، **عمليات لا تتكرر بنفس opId ولا يُحذف شيء — التصحيح بعملية عكسية**، تكلفة مباشرة تظهر للمسؤول فقط.
- **العمولات والأهداف:** ثابتة/متدرجة، استثناء لكل صنف، دفتر عمولات (`commissionLedger`)، صرف العمولة، مكافأة الأهداف.
- **الطلبات والرحلات:** طلبات الزبائن (رابط طلب + بوت واتساب)، تخطيط الرحلات، تتبع حي، تنبيه طلبات متأخرة.
- **CRM خفيف:** عملاء محتملون (Leads)، متابعات، عروض، قوائم أسعار، مجموعات زبائن.
- **الترحيل المحاسبي إلى «سيلا»** (`lib/silaPosting.js`): يُجهّز يوميًا فاتورة مجمّعة وإيصالات قبض ومصروفات ليُدخلها المحاسب يدويًا في نظام «سيلا» المحاسبي، مع بصمة لكشف أي تغيير بعد الترحيل.
- **الجودة الغذائية:** سجل درجات حرارة السيارات مع تنبيه.
- **الإدارة:** سجل تدقيق للفواتير (`invoiceAuditLog`)، تنبيهات، بث رسائل، صحة النظام، سجل أخطاء التطبيق.

### 1.3 نقاط القوة التي يجب الحفاظ عليها

1. **قواعد عمل ناضجة مكتوبة بخبرة الميدان** (تسوية السيارة، الحوالات المعلّقة، العمولة على المحصَّل فعلًا وليس المفوتر) — هذه معرفة تشغيلية لا تُعاد كتابتها من الصفر.
2. **مبدأ عدم الحذف والتصحيح بعملية عكسية** في التصنيع والفواتير — متوافق تمامًا مع تصميم GOLDEN ERP.
3. **العمل دون اتصال** (`offlineQueue.ts`): طابور محلي بالترتيب، تحقق من الوجود قبل الكتابة، حجز كتل أرقام للفواتير.
4. **تعديل/حذف الفاتورة عبر الخادم فقط** مع سبب إلزامي وسجل كامل.
5. **قوالب PDF عربية** (فاتورة، كشف حساب، سند قبض، تفقيط) — قابلة لإعادة الاستخدام كما هي.
6. **تكامل WhatsApp رسمي** (قوالب Meta، webhook، بوت).

### 1.5 الأمان (مراجعة سريعة)

- ✅ الأدوار عبر Firebase Custom Claims (يضبطها الخادم) وليس حقولًا يكتبها العميل.
- ✅ PIN المندوب مشفّر bcrypt ولا يُخزّن نصًا.
- ✅ الفواتير لا تُعدّل من العميل مباشرة (قواعد Firestore تمنع update/delete).
- ⚠️ لا يوجد Rate limiting صريح على دالة `repLogin` (Firebase يوفر حماية عامة فقط) — يُنصح بـ App Check.
- ⚠️ لا يوجد MFA للمسؤولين.

## 2. تقرير نظام «حضوري» (الحضور والانصراف والرواتب)

### 2.1 الحجم والمعمارية

| الجزء | التقنية | الحجم |
|---|---|---|

| الواجهة | React + Vite + TS (لوحة إدارة + صفحة موظف + Kiosk + مشرف) | 12,393 سطرًا؛ 31 صفحة |

| المحرك | `web/src/lib/engine.ts` مُجمّع إلى `functions/lib/engine.js` — **مرجع واحد لحساب الحضور والراتب في الواجهة والخادم** | — |

### 2.2 الوظائف الموجودة

- ملف الموظف (عام) + بيانات خاصة منفصلة (`employeePrivate`: الراتب، رمز الرابط) — **فصل جيد للبيانات الحساسة**.
- المواقع (Sites) بالخريطة، الأقسام، الدوامات والورديات (`computeDay`, `shiftFor`, `rosterMap`)، العطل الرسمية، أنواع الأعذار.
- البصمات من: الأجهزة، رابط هاتف الموظف (GPS)، QR في Kiosk، الإدخال اليدوي؛ **البصمة لا تُحذف بل تُلغى بسبب**.
- حالات اليوم: حاضر، متأخر، خروج مبكر، غير مكتمل، حضور يدوي؛ دقائق التأخير بعد السماح، الإضافي مع اعتماد.
- قرارات الموارد البشرية لكل يوم (غياب، عذر، تغطية، إذن، إعفاء).
- الإضافات الشهرية (مكافآت، سلف، بدلات)، **كشف راتب شهري يُقفل** (`payrolls/{YYYY-MM}`) ولا يُعدّل بعد الإقفال، قسائم رواتب.
- قراءة كشف حضور ورقي بالذكاء الاصطناعي (`readPaperSheet`) ثم اعتماده، مساعد جدولة.
- سجل تدقيق عام لكل كتابة (`audit` trigger على كل المجموعات).

### 2.3 نقاط القوة

1. **محرك حضور ورواتب واحد مشترك** بين الواجهة والخادم — يمنع اختلاف الأرقام.
2. **تكامل أجهزة ZKTeco فعلي** (ADMS + جسر للأجهزة القديمة) — قيمة كبيرة يصعب إعادة بنائها.
3. إقفال الشهر وعدم حذف البصمات — حوكمة جيدة.

## 3. ما يُدمج ويُعاد استخدامه

المبدأ: **لا نعيد بناء ما يعمل جيدًا دون سبب تقني واضح.** لكن قاعدة البيانات (Firestore أحادي المستأجر) لا تحقق شروط المنصة (قيود مرجعية، قيد مزدوج، عزل مستأجرين، معاملات)، لذا الإستراتيجية هي **Strangler Fig**: GOLDEN ERP يصبح نظام السجل (System of Record) تدريجيًا، والتطبيقات الحالية تستمر في العمل وتُربط به عبر محولات (adapters) حتى تُستبدل واجهاتها وحدةً وحدة.

| العنصر | القرار | السبب |
|---|---|---|
| قواعد عمل المناديب (تسوية السيارة، العمولة على المحصّل، الحوالات المعلّقة، المرتجعات) | **إعادة استخدام المنطق** — نقله كما هو إلى خدمات GOLDEN ERP مع اختبارات | معرفة تشغيلية مُختبرة ميدانيًا |
| تطبيق المندوب (Expo) | **الإبقاء عليه** وتحويل مصدر بياناته تدريجيًا إلى API GOLDEN ERP (المرحلة 4) | 32 شاشة تعمل، والمناديب معتادون عليها |
| طابور العمل دون اتصال + حجز كتل الأرقام | **إعادة استخدام التصميم**؛ API GOLDEN ERP يدعم `Idempotency-Key` لهذا الغرض تحديدًا | يمنع تكرار الطلبات عند المزامنة |
| قوالب PDF العربية + التفقيط | **إعادة استخدام كما هي** (مكتبة مشتركة) | لا داعي لإعادتها |
| تكامل WhatsApp (Meta Cloud API) | **إعادة استخدام** كخدمة إشعارات | يعمل ومعتمد من Meta |
| التصنيع المبسّط (`manufacturing.js`) | **مرجع للمتطلبات**؛ يُعاد تنفيذه بالكامل في وحدة التصنيع (BOM إصدارات، أوامر تشغيل، تكلفة، تتبع دفعات) | النموذج الحالي لا يدعم التتبع الأمامي/الخلفي ولا التكلفة الكاملة |
| الترحيل إلى سيلا | **يُستبدل** بالأستاذ العام في GOLDEN ERP (قيود تلقائية من المستندات) — بعد فترة تشغيل متوازٍ | يزيل الإدخال اليدوي المزدوج (V2) — **قرار يحتاج اعتمادكم** |
| محرك الحضور والرواتب (`engine.ts`) | **إعادة استخدام المحرك** بعد تغطيته باختبارات، ونقله إلى وحدة HR مع إضافة القيد المحاسبي | منطق دقيق ومُجرّب |
| تكامل ZKTeco (iclock + bridge) | **إعادة استخدام كما هو**، وتوجيه البصمات إلى API GOLDEN ERP | قيمة عالية، يعمل |
| بيانات الموظفين في النظامين | **توحيد**: جدول موظفين واحد في GOLDEN ERP؛ المندوب = موظف + دور مندوب | يزيل H3 |

### خطة الترحيل للبيانات (لاحقًا، بعد اعتماد البيانات)

لا تُنقل أي بيانات تشغيلية حقيقية إلى GOLDEN ERP قبل: (1) اعتماد دليل الحسابات من محاسب الشركة، (2) أرصدة افتتاحية معتمدة، (3) تشغيل متوازٍ لفترة يحددها المسؤول المالي.
